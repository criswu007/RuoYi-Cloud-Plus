# 标准地址/安装地址 ES 检索与高并发方案设计

## 1. 背景与目标

标准地址查询当前已存在两类明显瓶颈：

- 标准地址候选搜索与列表查询依赖 `ADDR_SEGM` 上的 `like '%keyword%'` 检索。
- 候选搜索链路存在 `order by segm_id asc`，在 230 万级数据量下容易被优化器拖成主键全表扫描。

当前业务目标已经明确：

- 标准地址候选搜索、标准地址后台列表、安装地址后台列表都要支持全局模糊搜索。
- 两类查询都要支撑高并发。
- 后台列表能力必须保留：多条件筛选、稳定分页、排序、导出同口径结果。
- 普通查询接口目标响应时间控制在 `1s` 内。
- 导出等大数据量接口允许 `30s` 级完成。

本设计聚焦搜索与读写一致性方案，不覆盖 UI 交互改版，也不覆盖跨系统检索平台化建设。

## 2. 已确认评估口径

以下内容已在本轮评估中确认，后续如需调整，应直接修改本节：

- 一致性按“业务上立即一致”评估，而非 `MySQL + ES` 的物理 `XA/2PC` 强一致。
- 在线写接口要求 `ES` 不可用时数据库写入也必须失败，不能接受“先写 DB、后补 ES”。
- 允许 `ES` 命中后再按当前页或当前批次回数据库补充明细字段，不要求把全部关联数据冗余到 `ES`。
- 标准地址与安装地址都要保留后台列表式能力，包括筛选、排序、稳定分页与导出同口径。
- 安装地址当前暂不要求大量实时衍生字段或复杂跨表实时状态。
- 普通接口以 `<1s` 为目标，导出接口以 `30s` 级为目标。

## 3. 现状证据

### 3.1 数据规模

- `ADDR_SEGM` 总量约 `2318018`，活跃数据约 `2197310`。
- `ADDR_SET_SEGM` 约 `100000`。
- `spc_region` 仅 `103` 行，性能瓶颈不在区域表。

### 3.2 已验证性能事实

- 标准地址候选搜索当前 SQL 形态为 `like '%keyword%'`，并带 `order by segm_id asc`。
- 在 `ADDR_SEGM` 上执行 `EXPLAIN ANALYZE`，实际会扫约 `232` 万行，耗时约 `5.6s ~ 6.3s`。
- 即使将 `segm_type` 收敛到约 `10963` 行，`order by segm_id` 仍可能导致优化器选择全表扫描。
- 去掉 `order by segm_id` 后，同条件执行时间约 `111ms`；强制走 `IDX_ADDR_SEGM_SEGM_TYPE` 时带排序约 `62ms`。

### 3.3 约束含义

- 当前瓶颈不只是“缺索引”，更是 `MySQL like '%x%' + 排序 + 高并发` 的查询形态本身不适合继续承担全局模糊检索。
- `region_id` 分布极不均匀，最大单区域约 `1573564` 行，“按区域收敛”只能缓解，不能单独解决问题。
- `stand_no/segm_no` 基本已填充，可作为拼音或编码前缀搜索的辅助字段。

## 4. 方案对比

### 4.1 方案 A：继续深挖 MySQL

做法：

- 重写 SQL，移除不必要排序。
- 强制索引或按 `segm_type/region_id` 分流。
- 针对安装地址继续补复合索引。

优点：

- 改造最小，不引入新读存储。

缺点：

- 对“全局模糊 + 高并发 + 列表/导出同口径”支撑不足。
- 标准地址 200 万级数据下，后续仍容易被深分页、模糊命中范围和排序条件拖垮。

结论：

- 不作为本轮推荐方案。

### 4.2 方案 B：ES 作为完整主读模型

做法：

- 查询完全走 `ES`，列表、导出、展示字段全部以索引文档为准。

优点：

- 读性能最好，数据库压力最小。

缺点：

- 文档字段会快速膨胀。
- 一致性复杂度和索引维护成本最高。
- 后续字段变更需要同步调整索引结构和回填逻辑。

结论：

- 适合字段稳定且读远多于写的成熟阶段，不是当前首选。

### 4.3 方案 C：ES 主检索，DB 批量补字段

做法：

- `ES` 负责模糊召回、筛选、排序、分页和导出结果集圈定。
- 返回结果以 `ES` 核心字段为主，缺失展示字段按页或按批次回 `MySQL` 补齐。

优点：

- 可以把全局模糊检索和高并发压力从数据库拿掉。
- 仍保留数据库作为明细与低频字段的权威源。
- 更容易兼顾普通接口 `<1s` 与导出 `30s` 级目标。

缺点：

- 需要设计双写、补偿、对账和索引修复机制。

结论：

- 本轮推荐方案采用方案 C。

## 5. 推荐方案总览

### 5.1 索引拆分

不建议标准地址和安装地址共用一个索引，推荐拆成两个独立索引别名：

- `address_standard_search`
- `address_installation_search`

物理索引采用版本化命名，例如：

- `address_standard_search_v1`
- `address_installation_search_v1`

后续全量重建时通过别名切换完成无停机替换。

### 5.2 字段边界

只要字段参与以下任一能力，就必须进入 `ES`：

- 全局模糊搜索
- 精确筛选
- 排序
- 稳定分页
- 导出结果集圈定

仅用于最终展示、低频查看或复杂关联补充的字段，可以保留在 `MySQL`，由服务层批量回填。

### 5.3 检索字段建议

标准地址索引至少包含：

- `segmId`
- `parentSegmId`
- `segmName`
- `standName`
- `segmNo`
- `standNo`
- `segmType`
- `regionId`
- `districtId`
- `serviceRegionId`
- `status`
- `createDate`

安装地址索引至少包含当前列表链路已使用的筛选/排序字段：

- `setAddrId`
- `setAddrName`
- `setAddrNo`
- `setType`
- `segmId`
- `segmType`
- `regionId`
- `orgId`
- `createDate`
- `associationStatus`

### 5.4 分词策略

默认推荐：

- 中文名称字段优先使用 `IK` 分词插件，建立 `ik_max_word` 索引分词与 `ik_smart` 查询分词。
- 编码或拼音类字段优先利用现有 `standNo/segmNo/setAddrNo`，通过前缀查询或 `edge_ngram` 子字段加速前缀检索。

若目标环境不能安装 `IK`，则退化为：

- 使用内置 analyzer + `ngram/edge_ngram` 子字段。

这个调整只影响字段 mapping，不改变整体架构。

## 6. 读链路设计

### 6.1 标准地址候选搜索

链路改为：

1. 请求进入候选搜索服务。
2. 对关键词做空白、全半角和大小写规范化。
3. 查询 `address_standard_search`，在 `segmName/standName/segmNo/standNo` 上执行模糊命中。
4. 叠加 `segmType/status/regionId` 等过滤条件。
5. 返回候选所需核心字段。

候选搜索本身字段较少，应尽量直接使用 `ES` 返回结果，避免每次候选都回库。

### 6.2 标准地址后台列表

链路改为：

1. 先查 `address_standard_search` 完成模糊命中、筛选、排序、分页。
2. `ES` 返回当前页 `segmId` 与核心展示字段。
3. 若页面仍需少量未入索引字段，再按当前页 `segmId` 批量回库。
4. 以 `ES` 返回顺序重排后响应。

### 6.3 安装地址后台列表

链路改为：

1. 先查 `address_installation_search`。
2. 关键筛选条件沿用现有后台语义：`setAddrName/setType/segmId/regionId/orgId/associationStatus/createDate`。
3. 排序保持与现有 SQL 一致：`createDate desc, setAddrId desc`。
4. 若仍需补标准地址名称或其他低频字段，再按当前页 `setAddrId` 或 `segmId` 批量回库。

### 6.4 导出链路

导出不再直接走数据库模糊查，改为：

1. 用与列表完全一致的查询条件先查 `ES`。
2. 使用 `PIT + search_after` 滚动拉取结果集，避免深分页。
3. 每批按 `id` 回库补齐导出所需字段。
4. 流式生成导出文件。

这样可以保证“列表和导出同口径”，同时规避 `MySQL offset` 深分页。

### 6.5 稳定分页与排序

排序统一遵循：

- 主排序字段按业务要求执行。
- 次排序统一补 `id`，防止同值记录跨页漂移。
- 参与排序的字段必须提前入索引。

后台列表仍保留页码分页，但应设置合理的 `max_result_window` 边界。超深分页不作为常规后台使用路径，超出阈值时建议通过导出满足取全量需求。

## 7. 写链路与一致性设计

### 7.1 一致性定义

本方案的一致性定义为：

- 写接口只有在 `ES` 和 `MySQL` 都成功后才返回成功。
- 接口成功返回后，新查询请求应能在 `ES` 中读到最新结果。
- 这属于业务上立即一致，不等价于存储层物理两阶段提交。

### 7.2 在线写入顺序

在线写链路统一推荐：

1. 读取旧快照。
2. 构造目标文档。
3. 先写 `ES`，在线接口使用 `refresh=wait_for`。
4. `ES` 成功后，再开启本地数据库事务写 `MySQL`。
5. `DB` 提交成功后返回成功。
6. `DB` 失败则立即执行 `ES` 补偿，并返回失败。

之所以采用“先 `ES`、后 `DB`”，是因为本轮口径明确要求“`ES` 不可用时数据库写入也必须失败”。

### 7.3 不同操作的补偿规则

- `create`：若 `DB` 失败，删除刚写入的 `ES` 文档。
- `update`：若 `DB` 失败，按旧快照回写 `ES` 文档。
- `delete`：若 `DB` 失败，将旧快照重新恢复到 `ES`。

如果补偿也失败：

- 当前请求仍返回失败。
- 同时落一条索引修复任务。
- 通过告警提醒运维或开发介入。

### 7.4 写入覆盖范围

标准地址写链路主要覆盖：

- `StandardAddressCommandService`
- `StandardAddressImportService`

安装地址写链路主要覆盖：

- `InstallationAddressServiceImpl`

建议抽出统一组件：

- `AddressSearchDocumentBuilder`
- `AddressSearchSyncService`
- `AddressSearchRepairService`

以避免标准地址和安装地址各自重复实现双写逻辑。

## 8. 全量重建、对账与修复

### 8.1 全量重建

全量重建建议流程：

1. 创建新的版本化物理索引。
2. 从 `MySQL` 全量扫描并批量写入新索引。
3. 校验总量、抽样校验关键字段、验证核心查询。
4. 通过别名一次性切换读流量。
5. 保留旧索引一段时间后再删除。

全量重建期间不走在线接口的 `refresh=wait_for` 逻辑，应走批量写入模式。

### 8.2 增量对账

仅依赖在线双写还不够，必须有对账机制：

- 对每次双写结果记录同步日志。
- 定时比对数据库与索引的数量、主键集合抽样和关键字段摘要。
- 对缺失、脏写、残留文档生成修复任务。

建议新增两类表或等价持久化结构：

- `address_search_sync_log`
- `address_search_repair_task`

### 8.3 修复策略

修复任务至少支持：

- 按主键重建单条文档
- 按主键删除脏文档
- 按业务类型批量重建某一批记录
- 按索引别名执行全量重建

## 9. 运行策略与默认降级原则

以下是本方案当前默认策略，后续可调整：

- 写路径不允许降级为“只写数据库”，`ES` 不可用时直接失败。
- 读路径默认不做“全局模糊自动回退数据库”，避免在 `ES` 故障时把数据库打穿。
- 如需保留极小流量的兜底能力，应限制为精确查询或受控后台开关，不作为默认路径。
- 导出依赖 `ES` 提供结果集圈定；`ES` 不可用时导出直接失败或排队，不建议自动切回数据库模糊导出。

## 10. 工程落地点

### 10.1 已有基础设施

仓库已经具备 `ES` 基础设施，可复用：

- `ruoyi-common/ruoyi-common-elasticsearch`
- `EasyEsConfiguration`

### 10.2 查询改造点

建议优先改造以下查询链路：

- 标准地址候选搜索：`StandardAddressSelectionServiceImpl`、`StandardAddressQueryService`
- 安装地址列表：`InstallationAddressServiceImpl`

现有 `Mapper XML` 中基于 `like '%x%'` 的链路应逐步下沉为：

- 仅用于回库补明细
- 或作为受控兜底开关

### 10.3 配置项

建议将以下参数配置化：

- 索引别名与物理索引前缀
- 在线写入是否 `refresh=wait_for`
- 批量写入大小
- `PIT` 保活时间
- 列表查询是否允许回库补字段
- 读兜底开关

## 11. 验收标准

本轮方案的验收口径建议固定为：

- 标准地址候选搜索、标准地址后台列表、安装地址后台列表满足普通接口 `<1s` 目标。
- 导出接口在当前数据规模下达到 `30s` 级目标。
- 列表与导出结果集口径一致。
- `ES` 写失败时，数据库写入不得成功。
- 数据库提交失败时，`ES` 能被同步补偿或进入可追踪修复队列。

## 12. 后续可调整点

为了方便后续修改，本方案刻意保留以下“调节旋钮”：

- 若未来允许最终一致，可把在线双写切换为 `DB + outbox + ES` 异步同步。
- 若未来列表展示字段趋于稳定，可把更多字段直接冗余到 `ES`，进一步减少回库。
- 若安装地址后续引入大量实时衍生字段，可把安装地址读链路收缩为“`ES` 只返回 `id`，DB 负责最终展示”。
- 若未来要支持更复杂的中文地址召回，可在不改写整体架构的前提下增强 analyzer、同义词、拼音或自定义词典。
