# 地址 ES 本地 standalone 联调与性能验收设计

## 1. 背景与目标

当前 `ruoyi-address` 已具备部分 ES 适配能力，但你本轮目标不是继续做抽象方案讨论，而是要把这套能力落到一条可实际执行的本地联调路径上：

- 使用 `script/docker/docker-compose.yml` 作为本地依赖清单。
- 继续采用 `standalone` 模式。
- `ruoyi-address` 业务事实源不迁移，继续直连本地可访问的 `ftth_cloud_address` 服务。
- 本地启动前后端完成联调，并让关键查询链路满足既有文档中的性能目标。

本设计聚焦三条明确链路：

- 标准地址查询
- 标准地址导出
- 安装地址查询

本轮不扩展到无关页面、不搭正式压测平台，也不把地址事实库整体迁入本地 MySQL。

## 2. 已确认决策

### 2.1 数据源决策

- `standalone` 环境继续直连本地可访问的 `ftth_cloud_address` 服务。
- `script/docker/docker-compose.yml` 中的 `mysql` 不是本轮地址查询的事实源。
- 本轮不设计地址库本地初始化、不做全量历史数据迁库。

### 2.2 联调决策

- 前端与后端都在本地启动联调。
- 本地容器依赖以 `redis`、`elasticsearch`、`kibana` 为主。
- `script/docker/docker-compose.yml` 已存在 `elasticsearch` 与 `kibana` 段，本轮重点是校准配置、启动顺序和 smoke 验证，而不是从零新增服务。

### 2.3 验收决策

- 验收口径采用“本地联调可跑通 + 关键查询/导出链路切到 ES + 本机 smoke/抽样压测证明时延稳定达标”。
- 不要求本轮补正式压测平台、持续监控大盘或完整性能报告。
- 性能目标沿用 `ruoyi-modules/ruoyi-address/docs/project-baseline.md` 中的既有要求，重点关注查询类接口与页面查询渲染的 `<=5s` 目标。

## 3. 现状与约束

### 3.1 配置现状

- `script/docker/docker-compose.yml` 已包含 `mysql`、`redis`、`elasticsearch`、`kibana` 等服务段。
- `ruoyi-modules/ruoyi-address/src/main/resources/application-standalone.yml` 已包含本地 ES/Kibana 地址及 `address.search.*` 读写开关。
- 当前 `address.search.standard.read-enabled/write-enabled` 与 `address.search.installation.read-enabled/write-enabled` 默认仍处于关闭状态。

### 3.2 模块约束

- `ruoyi-address` 查询链路必须遵守模块级 `AGENTS.md`：
  - 高数据量分页/搜索主查询禁止无必要自关联和跨事实表大 join。
  - 列表只查当前页必需字段，展示型衍生字段在服务层批量补齐。
  - 禁止逐条详情回查形成 N+1。
- 这意味着本轮 ES 适配不能只做到“能查”，还必须控制服务层补数策略。

### 3.3 已知能力缺口

- 标准地址导出虽然已有 `PIT + search_after` 基础能力，但导出字段合同与结果补齐还未完全闭环。
- 安装地址查询已具备基础 ES 分页读链路，但尚未完全满足 `docs/interface-checklist.md` 里的字段、筛选与权限口径。
- 因此本轮工作的真实重点是“补齐现有 ES 适配缺口并完成联调”，而不只是把服务启动起来。

## 4. 方案对比

### 4.1 方案 A：本地 standalone + ES 主查询 + DB 有界补齐

做法：

- 事实源继续走 `ftth_cloud_address`。
- 标准地址查询、标准地址导出、安装地址查询优先走 ES。
- 仅对 ES 文档中暂未建模且不参与主筛选/排序的展示字段做服务层批量补齐。

优点：

- 改动范围可控，最适合当前联调目标。
- 能直接对准查询性能问题，不引入额外数据搬迁复杂度。
- 便于分链路开启开关、逐项验证。

缺点：

- 需要先补齐安装地址查询和导出合同的 ES 文档能力。

### 4.2 方案 B：本地 standalone + ES 主查询 + 明确 fallback 框架

做法：

- 在方案 A 基础上，再把 DB fallback 做成更通用的运行态策略。

优点：

- 运行态回退更安全。

缺点：

- 实现复杂度更高，本轮为联调和达标而做会偏重。

### 4.3 方案 C：本地 standalone + 全量强制 ES 主读

做法：

- 目标链路一律只读 ES，不再保留 DB 查询主链路。

优点：

- 性能目标最直接。

缺点：

- 对当前未补齐的安装地址查询和导出链路风险过高。

### 4.4 结论

本轮采用 **方案 A**：

- 用最小必要改造完成本地联调。
- 让标准地址查询、标准地址导出、安装地址查询三条链路优先走 ES。
- 对未进索引但又确有展示必要的少量字段，只允许服务层批量补齐，不退化成 DB 主查询。

## 5. 推荐设计

### 5.1 联调架构

- 本地容器层启用 `redis`、`elasticsearch`、`kibana`，必要时连同已有平台依赖一起启动。
- 后端使用 `standalone` profile 启动 `ruoyi-modules/ruoyi-address`。
- 前端启动 `ruoyi-address-ui` 本地开发环境。
- 地址业务事实继续来源于本地可访问的 `ftth_cloud_address`，ES 只承担读模型与检索加速职责。

### 5.2 接口分流策略

#### 5.2.1 标准地址查询

- 列表分页主查询切到 ES。
- ES 文档负责完成模糊命中、筛选、排序与分页。
- 页面必需但不适合作为索引主字段的展示信息，在服务层按当前页批量补齐。
- 返回顺序以 ES 命中顺序为准，禁止补齐后打乱顺序。

#### 5.2.2 标准地址导出

- 导出结果集主来源切到 ES。
- 遍历方式继续采用 `PIT + search_after`，避免深分页性能退化。
- 导出字段合同缺失的部分，优先补充 ES 文档建模；确属低频展示字段时允许按批次批量补齐。
- 不允许因为导出字段缺口而回退为全量 DB 扫描导出。

#### 5.2.3 安装地址查询

- 分页查询优先走 ES。
- 必须按 `docs/interface-checklist.md` 对齐筛选字段、返回字段和权限/区域约束。
- 若页面仍需个别衍生字段，按当前页 `setAddrId` 或 `segmId` 批量补齐。
- 主筛选条件和主排序条件必须直接在 ES 中完成，不允许后置到数据库。

### 5.3 ES 与 DB 边界

- ES 负责：
  - 模糊搜索
  - 精确筛选
  - 排序
  - 稳定分页
  - 导出结果集圈定
- DB/事实源负责：
  - 权威事实存储
  - 少量低频展示字段补齐
  - 重建索引时的全量数据来源

边界约束：

- 禁止把大结果集先从 DB 查出再“写回 ES 风格分页”。
- 禁止逐条回查详情补字段。
- 禁止把区域/权限过滤留到 ES 查询之后再做内存裁剪。

### 5.4 运行态开关

- 保留并使用 `application-standalone.yml` 中的能力开关。
- 开启顺序按链路分阶段推进：
  1. 标准地址查询 `read-enabled`
  2. 标准地址导出对应读链路
  3. 安装地址查询 `read-enabled`
- `write-enabled` 只在联调需要重建或写入索引时按需开启，不默认无差别打开。

### 5.5 本地联调流程

推荐执行顺序：

1. 校验 `docker-compose` 中 ES/Kibana 的宿主机挂载路径、端口与 `host` 网络模式。
2. 启动 `redis`、`elasticsearch`、`kibana`。
3. 用 `standalone` profile 启动 `ruoyi-address`。
4. 通过现有 ES 运维/重建能力构建标准地址与安装地址索引。
5. 启动 `ruoyi-address-ui`，只验证目标查询页、导出入口和 ES 运维页。
6. 做 smoke 查询与抽样时延验证。

### 5.6 性能验收

本轮不做正式压测平台，采用本机 smoke/抽样压测验收：

- **标准地址查询**
  - 验证常用筛选组合与关键词检索返回正确。
  - 多次抽样调用下接口耗时稳定控制在目标范围内。
- **安装地址查询**
  - 验证文档规定的关键筛选字段、权限区域约束与分页顺序。
  - 多次抽样调用下接口耗时稳定控制在目标范围内。
- **标准地址导出**
  - 验证导出字段口径与列表查询一致。
  - 验证 ES 遍历链路可完成中大结果集导出，且不回退为 DB 全表扫描。

联调页面验收重点：

- 页面首屏查询和常规检索响应不超过 `5s`。
- 导出操作可被正常触发并返回正确文件。
- ES 运维台可用于索引状态检查与重建触发。

## 6. 错误处理

- ES 不可用、别名未绑定或索引不存在时，接口必须返回明确错误，不允许静默退回高风险 DB 全量扫描。
- 重建索引前应先做健康检查，避免前端联调阶段把“索引没准备好”误判成业务查询错误。
- 对服务层批量补齐失败的场景，应保留可诊断日志，便于区分“ES 命中失败”和“补齐失败”。

## 7. 测试与验收口径

### 7.1 后端测试

- 为标准地址查询 ES 网关补充分页、排序、字段映射与区域过滤测试。
- 为标准地址导出补充 `PIT + search_after`、批量补齐、导出合同一致性测试。
- 为安装地址查询补充筛选字段、权限区域约束、分页顺序和结果映射测试。
- 为 `standalone` 配置补充本地 Redis/ES/Kibana 绑定 smoke 测试。

### 7.2 前端验证

- 验证标准地址查询页、安装地址查询页与导出入口是否按预期调用目标接口。
- 若改动 `ruoyi-address-ui`，按模块规则必须重启前端项目后再验证。

### 7.3 联调验收

- 容器可启动。
- 后端 `standalone` 可启动并连通本地 Redis/ES/Kibana。
- ES 索引可重建并可通过运维能力确认状态。
- 前端可完成标准地址查询、安装地址查询与标准地址导出联调。
- 抽样验证表明关键查询链路稳定满足查询性能目标。

## 8. 风险与非目标

### 8.1 主要风险

- 安装地址查询字段口径若未补齐，容易出现“查得快但结果不对”。
- 标准地址导出若继续依赖过多 DB 回填，导出耗时会重新失控。
- 若在 ES 查询后才做区域/权限裁剪，会造成结果页不稳定或时延不可控。

### 8.2 非目标

- 不在本轮建设完整性能压测平台。
- 不在本轮迁移地址事实源到本地 MySQL。
- 不在本轮扩展无关页面或无关接口到 ES。
- 不在本轮做与本地联调无关的大规模重构。

## 9. 实施输出

完成本设计后，后续实现应交付：

- 一套可重复执行的本地 standalone 联调路径。
- 三条目标链路的 ES 适配补齐代码。
- 对应后端测试与本地 smoke 验证结果。
- 可用于人工验收的前后端联调步骤与性能抽样记录。
